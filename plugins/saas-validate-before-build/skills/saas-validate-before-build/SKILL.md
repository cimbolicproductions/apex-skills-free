# SaaS Validate Before Build

## When to Use This Skill

- The user asks whether they should build an idea.
- The user wants a landing page, fake-door test, waitlist, deposit test, or pre-sell plan.
- The user has not proven painful demand with real prospects.

## When Not to Use This Skill

- The product is already live and the user asks about retention or activation.
- The task is pure implementation of a validated feature.

## Intake Questions

Ask only for missing information that changes the output. If enough context exists, proceed and state assumptions.

- Who has the problem and what painful event triggers the search for a solution?
- What do they use today and what does it cost them?
- What proof would convince you to build: conversations, deposits, LOIs, pilots, or paid trials?

## Operating Workflow

- Write the problem hypothesis, ICP, current workaround, and willingness-to-pay assumption.
- Apply the 20-complaint rule: find recent public complaints before designing the solution.
- Choose the strongest feasible validation signal: paid deposit, signed pilot, LOI, booked call, email waitlist, or click.
- Design a fake-door or pre-sell funnel with one primary CTA.
- Write customer interview questions that avoid leading with the solution.
- Set go/no-go thresholds before launching the test.
- Recommend killing, narrowing, or building based on signal quality.

## Output Contract

Always produce practical artifacts the user can copy, paste, configure, or hand to a contractor.

- Validation plan.
- Landing page or fake-door copy.
- Interview script.
- Signal scorecard and go/no-go rule.

## Quality Checklist

Before finalizing, verify:

- Money or time commitment is weighted above compliments.
- Questions ask about past behavior, not hypothetical interest.
- The plan can run in 7 to 14 days.
